Verified against the actual repository (not the specs' self-reported line numbers). Overall the six specs are unusually accurate about existing code — nearly every cited file:line checked out exactly (terrain.js ZONES, GAPS, decorator gates; packages.js PACKAGE_TYPES/carry-spring constants; director.js timers; controller.js constants; cablecar.js structure; hud.js/index.html; verify.mjs assertions; package.json/vite.config/deploy.yml). The real risk in this design is not "the specs misread the code" — it's that **six specs were written in isolation and at least four of them rewrite the same files with incompatible, non-overlapping-aware designs.** That's where the actual blockers are.

## 1. Factually wrong claims

**[serious] shift spec's worked quota numbers are wrong.** Its table computes `Σ linePar` for shift 1 using invented spot heights "≈20/38/57/78/100/122/144/163 m at SPOT_TS (deliveries.js:6)". Recomputing the real formula (`terrain.js:104`, `h = PEAK * Math.pow(t,1.25) * 0.97 + 1.5`, PEAK=170) for the actual `SPOT_TS = [0.12,0.22,0.33,0.45,0.56,0.68,0.8,0.92]` (deliveries.js:6) gives **13.1 / 26.4 / 42.8 / 62.3 / 81.4 / 103.4 / 126.3 / 150.1 m** — 30-50% lower than what the spec used. Shift 1's stated quota "530" should be ~465; every "clean-chain revenue" estimate in that table is off by a similar margin. Not fatal (quota is derived programmatically from real `spot.pos.y` at runtime, so the code works), but the balance numbers presented as fact throughout §A are fabricated and will mislead whoever tunes `QUOTA_SLACK`.

**[serious] perf spec's justification for not instancing crates is technically wrong.** perf spec §D.1 explicitly excludes `props.js` crates (11 draw calls) from instancing, reasoning: *"physics.track(body, null) supports a null mesh but entry.pos carries no rotation (physics.js:88), so tumbling crates would lose their spin."* That's true only for the `mesh=null` case. Confirmed in physics.js:87-91 (`track`) and 98-124 (`syncMeshes`): when a real `THREE.Object3D` is passed as `mesh` (not `null`), `syncMeshes` writes `s.mesh.quaternion.copy(...)`/`.set(...)` onto it every frame — full rotation preserved. This is *exactly* the "proxy Object3D as mesh" technique art spec's own `InstancedPool` class uses for cablecar gondolas and terrain islands (art spec §G.2/§D.3, correctly reasoned: *"A bare THREE.Object3D satisfies that contract without being in the scene graph"*). perf spec never considers this option for crates, so its stated technical blocker is false — crates could be safely instanced. Their "not worth 11 draw calls" cost/benefit conclusion may still be fine, but it's dressed up with an incorrect constraint.

**[minor] Several off-by-a-few-lines citations**, harmless individually but worth flagging since the task demanded verification: shift spec's `director.js:26 this._eventTimer = 14` is actually line 24. mech spec's `controller.js:26 this._puntCd = 0` is actually line 27. None of these change any conclusion.

## 2. Architectural collisions (the real problem)

**[BLOCKER] Two complete, incompatible post-processing/quality systems both claim `src/fx/post.js` and `ctx.post`.**
- art spec: `new Post(renderer, scene, camera)`, constructed synchronously at module scope after the light rig (before `boot()` runs). Pipeline: `RenderPass → UnrealBloomPass → OutputPass → GradePass`. Keeps `renderer.toneMapping = ACESFilmicToneMapping` (main.js:25) untouched — deliberately, because `OutputPass` reads it. Its own tier auto-adjust lives in `Post.tick(dt, fps, tierCap)`.
- perf spec: `new Quality(ctx)` + `new Post(ctx)`, constructed as the *first two lines inside* async `boot()` (before `new Sfx()`). Pipeline: `RenderPass → [Bloom] → [FXAA] → GradePass` where `GradePass` **replaces** `OutputPass` and does its own inline ACES — requiring `renderer.toneMapping = THREE.NoToneMapping` (perf spec explicitly overwrites main.js:25 to the opposite of what art spec mandates). Verified this matters: `WebGLRenderer.js:1800-1806` (checked directly) confirms tone mapping is applied only when `_currentRenderTarget === null`, so art spec's "leave it as ACESFilmic, OutputPass will apply it once" is correct *for its own pipeline* — and simultaneously proves perf spec's competing pipeline (no OutputPass) requires the opposite renderer state. Both are internally correct. They cannot coexist.
- Both also declare a `TIERS` table with the keys `low/medium/high` but *entirely different field shapes* (art: `{msaa,bloomRes,dpr,grain,shadowMap,shadowS}`; perf: `{maxDpr,maxPixels,shadowMapSize,shadowBox,shadowBias,msaa,bloom,bloomScale,...,decor,fogNear,...}` — 20+ fields).
- Both edit main.js:19-27, :85-90 (resize), :96-112 (ctx literal), :149 (startGame), :193-197 (idle-render branch), and :267 (final render call) with mutually unaware final versions of those exact lines.

A "senior engineer implementing straight from the spec" cannot merge these without inventing a reconciliation neither spec describes. **Fix**: pick one owner for `Post`/tier system before implementation starts; this needs to be resolved at the human-decision level, not coded around.

**[BLOCKER] art §G and perf §D are two independent, competing full rewrites of the same five files' geometry, both converting the same targets to InstancedMesh:**
- terrain.js clouds (terrain.js:505-522), floating islands (terrain.js:295-314), crystals (terrain.js:378-394), birds (terrain.js:489-503)
- cablecar.js stations (:37-49), pylons (:99-121), gondolas (:129-169, :187-211)
- props.js mushrooms (:188-220, :319-354), pendulums (:82-125), crates (:290-306)
- deliveries.js huts (:63-72)

Confirmed by direct read: art spec's §G.2 defines `class InstancedPool` in a new `src/art/instanced.js`; perf spec's §D.1-D.4 does the *same* conversions with hand-rolled `this._im`/`this._imMax`/`this._cloudBlobs` fields directly on `Terrain`, no shared helper, different geometry-bake math shown in full code (§D.2), different draw-call targets (art: "89→7" for cablecar; perf: "89→7" — same number, different mechanism and field names). Both preserve `gondola.group`/`island.group` as pose carriers for verify.mjs (both correctly identified that requirement independently), but the two implementations of *how* are not merge-compatible — same file, same line ranges, two authors, zero awareness of each other. This is a much larger collision than the Post one: it's ~4 files' worth of substantial rewrite duplicated wholesale.

**[BLOCKER] ui spec and i18n spec directly contradict each other on the five most-used Hud method signatures.** ui spec's §J.1 API table explicitly lists these under **"UNCHANGED SIGNATURES (30 call sites across 5 files — do not touch)"**: `banner(textOrNull)`, `setPackage(name, note, hasShake=false)`, `setAlt(y, zoneName)`, `setTarget(relBearing, dist, name)`, `showSlip(num, def, targetName)`. i18n spec's §B "Required Hud changes" table mandates changing *those exact same five methods* to take translation keys instead: `banner(key, params)`, `setPackage(def, hasShake)`, `setAlt(y, zoneKey)`, `setTarget(rel, dist, nameKey)`, `showSlip(num, def, targetKey)` — with an explicit list of call sites to update (director.js:134,138,158,178; main.js:154; packages.js:373,413,472,487,489; deliveries.js:229,230). Verified real code: hud.js:30 `banner(text)`, :49 `setPackage(name, note, hasShake=false)`, :116 `setAlt(y, zoneName)`, :120 `setTarget(relBearing, dist, name)`, :137 `showSlip(num, def, targetName)` — confirms both specs are describing the *same real starting point* and prescribing opposite destinations. Whichever lands, roughly a third of the other spec's `hud.js` section is either wrong or dead on arrival.

**[serious] i18n spec's entire §E (CSS layout fixes) targets DOM ids ui spec deletes.** ui spec §I.4: *"Every rule at index.html:15-174 goes. The IDs #hud-hint, #hud-top-left, #hud-target, #hud-banner, #slip, #title-controls... are all retired."* i18n spec §E is ~11 subsections of German-text-overflow fixes keyed to exactly those ids (`#hud-hint` at index.html:125-128 confirmed real, `#slip` at :152-168 confirmed real, `#hud-top-left` at :55 confirmed real, etc.). If ui spec's markup rewrite lands, i18n §E is entirely inapplicable and must be redone from scratch against the new `ud-*` id namespace — nothing in either spec flags this dependency.

**[minor/serious] art spec's day-cycle lighting depends on a field the shift spec never produces.** art spec's `Mood.update(dt, playerY, flash, shift01)` is called as `mood.update(realDt, p.y, ctx.director.flash, ctx.shift01 ?? 0.35)` with the comment "Owned by the shift-structure workstream; defaults to mid-morning." Grepped the entire shift spec: it never defines, sets, or mentions `ctx.shift01` anywhere — its `Shift` class tracks `n`/`cursor`/`manifest`/`quota`, nothing resembling a 0-1 time-of-day scalar. If both land as written, `ctx.shift01` is permanently `undefined`, the `??` fallback pins it at `0.35` forever, and art spec's promised "warm morning → dusk across a shift" lighting arc silently never engages. Nobody would notice without reading both specs side by side.

**[serious] terrain.js `ZONES` array is rewritten twice with incompatible field names for a single shared consumer.** art spec §B.1 replaces `terrain.js:8-14` to derive `ZONES` from `art/palette.js`'s `BAND_KEYS`/`BAND_EDGES01`, keeping a `name:` field (English string). i18n spec §B replaces `terrain.js:9-13`'s `name:` field with `nameKey:` (translation key), explicitly noting *"Only consumer is deliveries.js:230 (verified by grep)"* — confirmed true by direct grep (deliveries.js:230 `hud.setAlt(p.y, zoneAt(p.y).name)` is the only reader). Both specs are rewriting the identical array declaration with incompatible schemas; whichever lands last silently reverts the other (either zone names never localize, or art's palette-derived band generation is lost).

**[serious] Three specs (i18n, shift, perf) each rewrite `startGame()`/main.js:146-158 as if it were the only one touching it.** Confirmed real starting point: main.js:146 `document.getElementById('title-screen').addEventListener('click', startGame, { once: true });`, main.js:149-158 `startGame()`. i18n spec rewrites :146 to a guarded self-removing handler carving out a language-switch button. shift spec rewrites the whole function to enter a `'briefing'` state and adds a `beginShift()` call. perf spec adds `ctx.quality.resetGrace(6); needsRepaint = true;` inside it. None of these three edits reference each other; a literal "apply spec X, then spec Y" workflow drops whichever patch was applied first unless someone manually diffs and merges by hand.

## 4. Perf claims that will not hold

**[serious]** If both art's `Post.tick()` and perf's `Quality.sample()` land, you get **two independent auto-quality-adjustment loops** both calling `renderer.setPixelRatio(...)` and touching shadow-map size every frame, driven by different signals (art: fps EMA with `_bad`/`_good` dt-accumulation; perf: p95-frame-time over a 120-frame window) and different hysteresis constants. Neither spec's oscillation-prevention analysis (art's "lock after one down→up→down cycle"; perf's "60s up-lockout, max 2 upgrades") accounts for a second system also mutating the same renderer state on alternating frames. This isn't a hypothetical — it's the direct, mechanical consequence of the Post/Quality collision above, and it invalidates both specs' "no oscillation" claims simultaneously.

**[minor]** perf spec's per-tier frame-budget tables ("≈6.1ms / 96fps", "8.5-10.5ms", "≈7-10ms") are computed from assumed memory-bandwidth figures (~220GB/s discrete, ~50GB/s Iris Xe) that are never sourced or benchmarked against this repo's actual scene. Presented with one-decimal precision, this is false confidence dressed as measurement — treat as an order-of-magnitude sanity check only, not a budget to hold anyone to.

## 5. Effort under-estimates

**main.js is the single most contested file across all six specs, and none of them says so.** Confirmed by direct citation-count: art touches main.js:1-14 (imports), :33-64 (sky), :72-91 (lights+construction), :195, :223-238, :240-252, :267. perf touches :1-14, :19-27, :76-90, :96-114 (new locals), :118-190, :193-197, :267, :277-292. shift touches :96-158 (state machine, ctx literal, boot ordering), :161-183 (pause), :277-292 (debug handle). ui touches "8 patch points" across the whole file plus index.html's markup and CSS wholesale. i18n touches :1-16 (module-scope init), :146, :149-158, :155/168/179/272 (string calls). mech touches none structurally but its new keybinds (`E`/`G`) insert into controller.js at the exact spots ui/shift/perf are simultaneously changing. **Every one of the six "implementation order" sections assumes it is applying to an otherwise-untouched main.js.** In reality, before any of them can even start, someone has to hand-merge five to six independent, unaware full rewrites of a 293-line file — none of the specs budget time for this, and it is not a mechanical merge (see the Post/tone-mapping and Hud-signature contradictions above, which are semantic, not textual, conflicts). Treat the real main.js integration cost as a standalone workstream, not a side effect of "landing the specs in order."

**shift spec underestimates its own verify.mjs surface.** Section I lists new checks N1-N12 as if they were the delta, but per the table above, at least three *existing* checks (recovery roll, walk-distance, boot timeout) are flagged as fragile by perf spec and never actually patched by anyone — that debugging/rewrite work isn't costed into either spec.

## 6. Order-of-operations traps

1. **art's ZONES-from-palette rewrite and i18n's ZONES nameKey rewrite must be done as a single, deliberately-merged edit** (e.g., `nameKey:` field driven by `BAND_KEYS.map(...)`), not sequentially — applying either one first and the other second on top produces a broken or half-localized zones array with no build error to catch it (it's a silently-wrong string, not a crash).
2. **i18n §E (all CSS overflow fixes) must be deferred until after ui's markup rewrite lands**, then entirely re-derived against the new `ud-*` ids — doing it in the original order (patch old ids, then have ui delete them) is pure wasted work.
3. **perf's shader warm-up (§E) explicitly must run after all InstancedMesh definitions exist** ("§E.3: `instanced` is a program define... warm-up must run after all instancing is built") — but per the art/perf instancing collision, *which* InstancedMesh definitions exist depends on which of the two competing rewrites was kept. Warm-up coverage and the eventual GLSL/program count are only knowable after that decision is made, not before.
4. **The Post/Quality/tone-mapping decision (finding #1 above) gates almost everything else** — art's sky-shader color values (§A.2 of art spec) are explicitly authored "for the corrected pipeline" (post-OutputPass gamma correction) and are stated to look wrong under the old direct-render path. Landing any art palette/sky work before the post-pipeline question is resolved one way or the other means re-tuning every hex value in `palette.js` afterward.

## Bottom line

Individually, each spec is well-researched against the actual code — line numbers, constants, and API shapes check out far more often than not, which is unusual and worth acknowledging. The actual risk in this project is not "the specs are wrong about the codebase," it's that **four of the six specs (art, perf, shift, i18n; ui and mech are comparatively more self-contained) independently rewrite the same handful of files — main.js, terrain.js, cablecar.js, props.js, hud.js/index.html — with designs that were each validated only against the *current* repo, never against each other.** A senior engineer implementing "straight from the spec" needs to pick one spec per contested subsystem before writing code, not merge all six in sequence; several of the collisions above (Post/tone-mapping, Hud signatures, ZONES schema) are semantic contradictions that will not surface as merge conflicts or type errors — they'll surface as silently wrong behavior (a sky that's still too dark, a HUD that shows `undefined` or a raw key like `hud.deliver_to`, a lighting cycle that never moves) that nobody will trace back to "two specs disagreed" without exactly this kind of side-by-side read.
